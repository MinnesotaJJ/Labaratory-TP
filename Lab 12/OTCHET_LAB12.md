## 1. Цель работы
Изучить различия между аутентификацией и авторизацией, принципы работы серверных сессий и JSON Web Token (JWT), жизненный цикл сессии и механизмы безопасного хранения токенов; разработать клиент-серверные прототипы с проверкой прав доступа на стороне сервера.

## 2. Схема работы (Вход → Проверка доступа/отказ → Выход)

```text
[Браузер (Клиент)]                        [Сервер (Node.js / Express)]
       |                                               |
       |--- 1. POST /api/login (login, password) ----->|
       |                                               |-- Валидация полей (400 при пустых)
       |                                               |-- Сверка хеша пароля (401 при ошибке)
       |<-- 2. Set-Cookie (HttpOnly) / Access JWT -----|
       |                                               |
       |--- 3. GET /api/profile (или /workspace) ----->|
       |                                               |-- Проверка сессии / подписи JWT / exp
       |                                               |-- Проверка прав доступа (401 / 403)
       |<-- 4. 200 OK (Защищенные данные) -------------|
       |                                               |
       |--- 5. POST /api/logout ---------------------->|
       |                                               |-- Удаление сессии / отзыв токена
       |<-- 6. 200 OK (Очистка cookie / памяти) -------|
```

## 3. Описание реализации и мер безопасности
1. **Разделение фронтенда и бэкенда:** Интерфейс реализован на чистом HTML5, CSS3 и модульном JavaScript (`public/`), а логика проверки учетных данных и защиты маршрутов вынесена на сервер (`server.js`).
2. **Хеширование паролей:** На сервере пароли не хранятся в открытом виде (используется `crypto.scryptSync` с индивидуальной солью в Варианте 1 и `SHA-256` в учебных целях в Вариантах 15 и 17).
3. **Защита от XSS и CSRF:**
   - В Варианте 1 идентификатор сессии передается только в cookie с флагами `HttpOnly` и `SameSite=Strict`.
   - В Вариантах 15 и 17 `Access Token` хранится исключительно в оперативной памяти JS (не в `localStorage`), а `Refresh Token` (Вариант 17) изолирован в `HttpOnly` cookie.
4. **Творческое дополнение:**
   - В интерфейсы добавлен **живой таймер обратного отсчета** оставшегося времени сессии/токена;
   - Реализован **серверный журнал аудита** попыток входа и ротации токенов;
   - Добавлено модальное подтверждение выхода и кнопки быстрой проверки сценариев `401` и `403`.

## 5. Ответы на контрольные вопросы

1. **Чем аутентификация отличается от авторизации?**  
   *Аутентификация* подтверждает личность пользователя (кто он такой — проверка логина и пароля), а *авторизация* определяет его права доступа к конкретным ресурсам и действиям (что ему разрешено делать — например, проверка роли `teacher` или принадлежности ID).
2. **Что такое JWT и из каких частей он состоит?**  
   JWT (JSON Web Token) — открытый стандарт компактного токена в формате Base64URL, состоящий из трех частей, разделенных точками: `Header` (алгоритм и тип токена), `Payload` (набор утверждений — claims) и `Signature` (криптографическая подпись).
3. **Шифрует ли JWT содержимое payload?**  
   Нет. Стандартный JWT (JWS) только кодирует `Header` и `Payload` в Base64URL и защищает их от изменения цифровой подписью. Любой может декодировать содержимое payload, поэтому в нем нельзя хранить пароли и секреты.
4. **Что такое серверная сессия?**  
   Механизм сохранения состояния пользователя на стороне сервера (в памяти, Redis или БД), при котором клиенту передается только случайный идентификатор сессии (`Session ID`) в cookie.
5. **Зачем нужны HttpOnly и Secure для cookie?**  
   `HttpOnly` запрещает доступ к cookie из клиентского JavaScript (`document.cookie`), защищая токен/сессию от кражи при XSS-атаках. `Secure` гарантирует передачу cookie исключительно по зашифрованному протоколу HTTPS.
6. **Почему localStorage не рекомендуется для хранения чувствительных токенов?**  
   Данные в `localStorage` доступны любому JavaScript-коду на странице. При наличии уязвимости XSS (межсайтовый скриптинг) злоумышленник сможет прочитать токен и отправить его на свой сервер.
7. **Чем OAuth 2.0 отличается от OpenID Connect?**  
   OAuth 2.0 — протокол делегированной *авторизации* (предоставление приложению доступа к API от имени пользователя). OpenID Connect (OIDC) — надстройка над OAuth 2.0, добавляющая слой *аутентификации* и стандартный `ID Token` (JWT) с информацией о личности пользователя.
8. **Что такое access token и refresh token?**  
   `Access token` — короткоживущий токен для непосредственного доступа к защищенным API. `Refresh token` — долгоживущий токен, используемый исключительно для безопасного получения новой пары токенов без повторного ввода пароля.
9. **Зачем проверять срок действия JWT?**  
   Проверка claim `exp` ограничивает окно возможностей злоумышленника в случае компрометации токена и заставляет клиента периодически обновлять сессию на сервере.
10. **В чем различие HTTP 401 и 403?**  
    `401 Unauthorized` означает, что пользователь не аутентифицирован (отсутствует или недействителен токен/сессия). `403 Forbidden` означает, что личность пользователя установлена, но у него недостаточно прав для доступа к запрашиваемому ресурсу.
11. **Почему нельзя полагаться только на скрытие кнопки в интерфейсе?**  
    Клиентский код (HTML/CSS/JS) полностью контролируется пользователем: кнопку можно отобразить через DevTools или отправить прямой HTTP-запрос через `curl`/Postman. Проверка прав должна выполняться на сервере при каждом запросе.
12. **Что должно происходить при выходе пользователя?**  
    Сервер должен уничтожить запись сессии или отозвать/поместить токен в черный список, отправить заголовок очистки cookie (`Max-Age=0`), а клиент — удалить токен из памяти и перенаправить пользователя на экран входа.
